# Claim G2 — scheduled-workflow inactivity disablement, and whether the workflow's own commits reset the clock

**Date checked:** 2026-09-09

## Method

1. WebFetch of GitHub's official docs on events that trigger workflows (the `schedule` event
   section).
2. WebSearch for community discussion of the specific sub-question (does a workflow's own
   commit count as activity).
3. WebFetch of one specific GitHub community discussion thread, checking for any GitHub-staff
   statement.

## Evidence

### (a) The threshold itself — official docs, confirmed

`https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows` (schedule
event section), fetched 2026-09-09, quoted verbatim:

> "In a public repository, scheduled workflows are automatically disabled when no repository
> activity has occurred in 60 days."

Also on that page: minimum interval "once every 5 minutes," runs use "the latest commit on
the default branch," and a cross-reference to
`/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows#enabling-a-workflow`
for manually re-enabling a disabled workflow — but that section is about manual reactivation,
not about what counts as activity that prevents disablement in the first place.

**This part is settled: 60 days, stated as official policy, for public repositories.**

### (b) Does the workflow's own commit count as activity? — NOT settled by official docs

The fetched page does not define "repository activity" anywhere in the `schedule` event
section. No numbered list of qualifying activity types, no explicit inclusion or exclusion of
bot/workflow-authored commits.

WebSearch turned up:
- Multiple GitHub Marketplace "keepalive" actions whose entire purpose is to make a small
  commit (e.g. touching a `last-active.txt` file or bumping a tag) specifically to prevent
  the 60-day disablement — e.g. `efrecon/gh-action-keepalive`
  ("Workflows will be automatically disabled by GitHub after 60 days of inactivity"),
  `PhrozenByte/gh-workflow-immortality`, and a DEV.to guide "How to prevent GitHub from
  suspending your cronjob based triggers." Wide community adoption of this pattern is
  circumstantial evidence it works, but it's evidence by revealed practice, not an official
  GitHub statement, and I did not find a source confirming these actions were tested to
  actually work versus just being a popular but unverified folk remedy.
- GitHub Community Discussion #86087 ("way to opt out of ... 60 days"), fetched directly: two
  non-staff participants (marklemay, jidanni), neither addressing what counts as activity.
  Verbatim: no GitHub employee/staff account posted in this thread. The discussion is
  explicitly noted in its own text as "unresolved on this technical question."
- GitHub Community Discussion #184653 ("It's a real pain to disable automatically disabled
  workflows") and Issue #50 on `fischerscode/DockerFlutter` were surfaced by search but not
  individually fetched/read in full — flagging so this isn't silently treated as checked.

## Conclusion

**Proposed status for (a), the 60-day threshold: VERIFIED** against GitHub's own current docs.

**Proposed status for (b), whether a workflow's own commit resets the clock: UNCHECKED.**
I did not find an official GitHub statement confirming or denying this, and I am not treating
the popularity of "keepalive" actions as sufficient evidence — that's a plausible inference
from revealed community practice, not a verified fact, and CLAIMS.md's own rule is not to
upgrade a claim to VERIFIED on the strength of a plausible inference. I have not marked it
UNCONFIRMED either, because I did not myself run a check that returned an inconclusive
result — I found no authoritative source to check against at all on this specific point, which
is UNCHECKED, not UNCONFIRMED.

## Proposed test (per the brief's instruction, since docs don't settle point (b))

Minimal empirical test the maintainer could run:

1. Create a scheduled workflow in this repo (or a disposable throwaway public repo) that does
   nothing but commit a trivial change (e.g. append a line to a heartbeat file) on a daily
   cron.
2. Make no other commits, pushes, releases, or PR merges to that repo for at least 65 days
   (comfortably past the stated 60-day threshold) — i.e. the *only* repository activity for
   that window is the workflow's own commits.
3. Check on day 65+ whether the workflow is still enabled and has kept running daily
   (visible in the Actions tab / via `gh workflow list` showing "active" status, and via the
   run history showing unbroken daily runs).
4. If it is still active and running, that confirms a workflow's own commit counts as
   activity and resets the clock. If it has been disabled despite daily commits, that refutes
   it, and a heartbeat action alone would not be sufficient — the maintainer would need some
   other qualifying activity (e.g. a manual dispatch or a genuinely external trigger) on a
   sub-60-day cycle.

This needs real wall-clock time (65+ days) and cannot be shortcut; it's a Session 6 concern
(scheduling), not something to resolve in this reconnaissance round.

## Confidence flag

Treat the "keepalive action" ecosystem as circumstantial, not confirmatory — many popular
GitHub Marketplace actions exist to work around problems people only ever partially
understand, and popularity is not proof of mechanism.
